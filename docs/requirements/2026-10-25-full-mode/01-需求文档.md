# 需求文档：DSH「全量模式」

- 编号：`2026-10-25-full-mode`
- 状态：已实现，验收见 [04-验收报告](04-验收报告.md)
- 提出人：用户
- 载体：DSH Web GUI 插件包 `.dsh-plugins/full-mode`

## 1. 背景与问题

用户在日常使用 DSH（`http://127.0.0.1:3080`）交付需求时，交付物依赖当次的对话过程：

1. 需求边界、验收口径只存在于聊天里，事后无法回看，也无法交给别人复核。
2. 测试是"顺手跑一下"，没有固定记录；用户看不到"到底怎么测的、测了哪些、失败在哪"。
3. 权限选择每次会话都要处理，遇到需要写文件/跑命令的步骤容易被打断。
4. 协作模式只有计划模式（`/plan`），没有面向"完整交付"的默认模式。

用户明确要求：**说出需求后，智能体自动整理需求文档、测试方案、测试报告、验收报告，并且要能看到测试是怎么做的；每个需求默认做这四步；权限用全量权限。**

## 2. 目标与成功标准

目标：把"四份文档 + 真实测试证据 + 全量权限姿态"固化成 DSH 的一个**默认生效**的模式，不依赖用户每次提醒。

成功标准：

1. 模式对交付类需求默认生效，无需用户每次声明；
2. 每个交付类需求结束后，仓库固定位置出现四份非空文档；
3. 四份文档之间有可追溯编号链：需求点 R → 验收标准 AC → 用例 T → 证据；
4. 测试报告中的命令与输出可复制重跑，失败原样保留；
5. 界面存在可见的模式标识与命令入口，用户能确认自己处于该模式。

## 3. 用户场景

- **S1 新需求**：用户说"加一个微信登录"，Agent 先写需求文档与测试方案，再实现，跑测试，出测试报告与验收报告，回复里给四份文档链接。
- **S2 缺陷修复**：用户贴一个报错，Agent 按同一流程交付，测试报告包含复现命令、修复前后输出。
- **S3 抽查**：用户想知道"上次那个需求到底测了什么"，直接打开 `docs/requirements/<日期>-<短名>/03-测试报告.md`。
- **S4 降级**：用户说"这个不用写文档，只改一行"，Agent 跳过并说明。

## 4. 需求点

| 编号 | 需求 | 落点 |
| --- | --- | --- |
| R1 | 模式默认生效，不依赖每次声明 | 宿主全局提示词段落（常开） |
| R2 | 四件套固定命名与顺序：`01-需求文档` → `02-测试方案` → `03-测试报告` → `04-验收报告` | 段落中的目录约定 |
| R3 | 需求点 R 与验收标准 AC 编号化、可测 | 段落中的编号要求 |
| R4 | 测试方案先于或同步于实现 | 段落中的顺序要求 |
| R5 | 测试报告含真实命令、真实输出、用例结果表、证据文件 | 段落中的证据规则 |
| R6 | 验收报告逐条 AC 结论 + 证据链接 | 段落中的验收表要求 |
| R7 | 界面可见：输入框下方模式徽标 + `/full` 命令 | 客户端 `conversation.composer.dock` + 宿主命令 |
| R8 | 全量权限姿态：非不可逆操作不再逐条征求同意 | 段落中的执行规则 |
| R9 | 可关闭：停用插件即完全退出 | bundle 卸载 |

## 5. 非目标

- 不做强制门禁：不拦截工具调用、不阻塞写文件，模式是提示词引导而不是沙箱。
- 不修改沙箱/审批服务本身的默认值（新会话默认权限仍由 DSH 设置决定）。
- 不为每个需求单独做权限开关。
- 不要求子智能体重复产文档（文档由主 Agent 汇总）。

## 6. 边界与约束

- 依赖 DSH 插件面：bundle patch、`systemPrompt.section`、`commands.register`、Client slot 注册。
- 依赖 `pnpm`（插件安装由 Plugin Manager 调用）。
- 段落常驻系统提示，每个请求增加 1039 字符（实测，21 行，约 700–1000 tokens）。
- 子智能体会话通过 `session.header.origin` / `delegationDepth` 判定并跳过。

## 7. 验收标准

| 编号 | 验收标准 | 判定方式 |
| --- | --- | --- |
| AC1 | 插件包安装成功，profile 依赖与 bundle 列表包含它，应用状态 `applied`、无 warning | install_bundle 返回 + profile `package.json` |
| AC2 | 宿主系统提示中出现「全量模式」策略段落 | 会话日志 `system/message` 事件 |
| AC3 | 子智能体会话不出现该段落 | 子会话日志扫描 |
| AC4 | 客户端 `conversation.composer.dock` 出现 `full-mode-chip` 且 `active` | `Slots.listSubTree` |
| AC5 | `/full` 命令注册成功，返回规范摘要 | 插件 applied 未抛错 + 用户侧 `/` 菜单 |
| AC6 | 输入框下方徽标正常渲染 | 页面目视（无浏览器控制时标注未验证） |
| AC7 | 停用插件后段落与徽标同时消失 | 卸载验证（本轮不做，避免破坏已验证环境） |
| AC8 | 本需求本身按四件套交付 | 本目录四份文档 |

## 8. 依赖与风险

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 机器未安装 `pnpm` | 插件安装直接失败 | 已安装 `pnpm 10.34.8` 并记录 |
| 提示词常驻增加 token 成本 | 每请求多约 500–700 tokens | 段落已压缩；纯问答也带这段 |
| 提示词是引导不是强制 | 极端情况下可能漏写文档 | 由用户在验收时检查四份文件；后续可加校验工具 |
| 子智能体判定依赖 session header 字段 | 字段缺失时子会话也会带段落 | 双重判断 `origin === 'subagent'` 或 `delegationDepth > 0` |
| 端口页面需要认证链接 | 无法自动截图 | 验收时由用户目视确认 |
