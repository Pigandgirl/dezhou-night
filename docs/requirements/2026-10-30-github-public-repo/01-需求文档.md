# 01 需求文档：项目上传 GitHub 公开仓库

- 日期：2026-10-30
- 仓库：`Pigandgirl/dezhou-night`（公开）
- 执行人：AI 编码代理（DSH）
- 状态：进行中（测试与验收结果见 03、04）

## 1. 背景与问题

`D:\software\project\dezhou` 是《德扑之夜》的完整工程（Web 前端、Node 服务端、Android 壳、iOS 壳、测试脚本与需求文档）。当前状态：

- 本地 git 仓库只有 `master` 分支和 3 条历史提交，**没有任何远程仓库**，代码仅存在于本机；
- 工作区约 **891.68 MB**（不含 `node_modules`），其中大量是构建/测试产物：`android/*.apk` 约 219.7 MB、`server/public/apk` 约 208.1 MB、`qa/out` 约 264.6 MB、`docs` 证据图约 70.0 MB、`tools` 约 61.4 MB；
- 工作区包含敏感材料：`android/dezhounight.keystore`（APK 签名密钥，已进入 `master` 最新提交）、`tools/lhr_key`（OpenSSH 私钥），以及构建脚本中硬编码的签名口令；
- 根目录没有 README，公开仓库无法直接说明项目用途与启动方式。

直接 `git push` 全量内容会带来三个问题：GitHub 体积/单文件限制、私钥与签名密钥泄露、公开仓库被无关产物淹没。

## 2. 目标与成功标准

在 GitHub 账号 `Pigandgirl` 下新建公开仓库 `dezhou-night`，用一条干净的历史提交上传**可运行的源码、构建配置与文档**，同时确保任何密钥、私钥、安装包与测试产物都不进入公开仓库；克隆仓库后能够按 README 完成本地启动与构建。

成功标准：

1. 仓库公开可匿名访问，默认分支 `main`；
2. 远程文件树包含前端、服务端、Android/iOS 工程、脚本、测试脚本与文档；
3. 远程不含 keystore、SSH 私钥、APK/IPA、`node_modules`、`dist`、`qa/out`；
4. 仓库体积控制在 200 MB 以内；
5. README 能引导完成本地运行、构建、测试与部署；
6. 快照内 `npm run build` 与 `node server/server.js` 可正常执行。

## 3. 用户场景

- **新开发者**：`git clone` 后按 README 执行 `npm install`、`node server/server.js`，打开 `/play` 试玩；
- **维护者**：在另一台机器拉取代码，继续开发与打包 APK；
- **浏览者**：在 GitHub 页面了解项目功能、技术栈、目录结构与文档；
- **安全审计者**：确认仓库没有签名密钥、SSH 私钥、生产数据与安装包。

## 4. 需求点

### R1 新建公开仓库

在 `Pigandgirl` 账号下创建公开仓库 `dezhou-night`，默认分支为 `main`，不自动生成 README/LICENSE。

### R2 上传源代码与构建配置

包含：根目录 `index.html`、`src/`、`public/`、`shared/`、`server/`（服务端代码、`lib/`、`shared/`、`public/web`、`public/admin`、`public/app/latest.json`、systemd unit、TTS 脚本）、`android/app/` 与 `android/version.json`、`ios/`、`scripts/`、`deploy/`、`qa/` 测试脚本、`package.json`、`package-lock.json`、`vite.config.js`、`.github/workflows/`。

### R3 上传文档与发布记录

包含根目录 `README.md`、`docs/requirements/`（历史需求四件套与证据）、`RELEASE-*.md`、`QA-测试报告.md`、`QA-修复报告.md`、`界面改造说明.md`、`docs/wechat-login-and-payment-integration.html`。

### R4 排除构建产物与二进制

不提交 `node_modules/`、`dist/`、`qa/out/`、`.tmp-ios-ci/`、`.trae*/`、`.dsh-plugins/`、`tools/`、`server/public/apk/`、`*.apk`、`*.idsig`、`*.ipa`、`*.sha256`。

### R5 排除密钥与证书材料

不提交 `android/dezhounight.keystore`、`tools/lhr_key`、`tools/lhr_key.pub`、`*.pem`、`*.key`、`*.p12`、`.env*`；构建与部署口令通过环境变量注入。

### R6 重建干净历史

公开仓库使用全新的 `main` 历史：一条初始提交承载源码与文档，验收后追加文档更新提交；不推送含 keystore 的 `master` 历史；本地 `master` 保留不动，避免破坏现有工作。

### R7 根目录 README

说明项目简介、功能、技术栈、目录结构、本地启动、Web/Android/iOS 构建、测试、部署、文档索引，以及公开仓库的排除项与免责声明。

### R8 推送后远程校验

验证仓库可见性、默认分支、文件树、体积、匿名访问，并确认敏感文件不在远程。

### R9 过程文档

按全量模式产出 `01-需求文档.md`、`02-测试方案.md`、`03-测试报告.md`、`04-验收报告.md`，随仓库一起提交。

## 5. 边界与非目标

- 不修改游戏业务代码、不升级依赖、不改变构建产物逻辑；
- 不部署生产、不操作 `192.144.159.220:8080` 服务器、不执行 `scripts/deploy_server.py`；
- 不配置 GitHub Actions Secrets、不触发 TestFlight 上传；
- 不创建 GitHub Release、不上传 APK 到 Release；
- 不添加开源许可证（是否开源授权由作者决定）；
- 不对历史文档中的生产 IP/域名做批量脱敏（属于历史资料），仅在 README 提示替换；
- 不保证公开仓库可直接产出与线上一致的签名 APK（签名密钥刻意排除）；
- 不迁移旧提交历史、issue、PR。

## 7. 依赖与风险

| 项 | 说明 | 应对 |
|---|---|---|
| GitHub 认证 | `gh` 已登录 `Pigandgirl`，token 具备 `repo` scope | 推送前 `gh auth status` 复核 |
| 网络 | 约 100 MB 数据推送到 GitHub，跨境链路可能慢或中断 | 后台执行、失败重试、必要时改用 SSH |
| 仓库体积 | 文档证据约 70 MB，仓库约 100 MB | 排除 APK/测试产物，控制在 200 MB 内 |
| 密钥泄露 | keystore 在 `master` 历史中；`tools/lhr_key` 是 SSH 私钥 | 新建 orphan `main`、只推 `main`、`.gitignore` 兜底、远程树复核 |
| 签名口令 | `scripts/build-apk.ps1` 中硬编码口令（keystore 不公开，单独泄露口令无法伪造签名） | 在 04 中记录为遗留风险，建议后续改为环境变量 |
| 生产信息 | 文档/发布记录包含生产 IP 与 HTTP 地址 | README 提示替换域名并启用 HTTPS；不改历史资料 |
| GitHub Actions | 推送 `main` 会触发 `iOS Build`（macOS） | 不阻塞交付，结果记录到 03/04 |
| 权限 | 用户批准公开仓库；签名密钥与私钥不公开 | 已在方案中默认执行 |
