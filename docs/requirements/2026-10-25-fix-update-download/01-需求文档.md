# 修复更新下载失败需求文档

## 背景与问题

用户停留在 1.0.82，打开更新弹窗后点击「立即更新」，界面显示：

```text
下载进度：失败
下载失败，请重试
```

但只有「重试下载」和「浏览器下载」，App 内无法完成下载与安装。

旧实现存在两条网络路径：

1. Android `DownloadManager`；
2. `HttpURLConnection` 直连。

两条路径都依赖 Android 原生网络栈。生产环境 APK 使用 HTTP 地址，且设备/系统下载器策略可能拒绝下载，导致失败。旧版没有第三条可用通道，也没有把 APK 内容通过已验证可用的 WebView 网络通道取回。

## 目标与成功标准

- 更新 APK 必须通过游戏页面已经验证可用的 WebView 网络栈下载；
- 下载数据必须能安全写入 Android 私有更新目录；
- 下载过程有真实进度；
- 下载完成后自动打开系统安装器；
- 任一环节失败都必须明确提示，并保留浏览器下载兜底；
- 后续版本不再依赖 DownloadManager/HttpURLConnection 才能更新。

## 用户场景

1. 用户打开旧版，被提示必须更新；
2. 点击「立即更新」；
3. 页面用 fetch 从服务器读取 APK；
4. 每 64KB 把数据交给 Android 写入更新文件；
5. 进度条从 0% 增长到 100%；
6. 下载完成后出现系统安装界面；
7. 安装完成，后续版本可继续使用同一通道更新。

## 编号需求点

- **R1**：优先使用 WebView `fetch` 获取 APK，不再把 Android 原生下载器作为首选。
- **R2**：APK 数据分片传给 Android，每片最大 64KB，避免一次 JS Bridge 传递 1MB 以上字符串。
- **R3**：Android 端用 `beginWebUpdate` / `appendWebUpdate` / `finishWebUpdate` / `abortWebUpdate` 管理文件。
- **R4**：下载进度按已接收字节 / Content-Length 实时显示。
- **R5**：WebView 下载失败时显示失败状态、重试按钮和浏览器下载按钮。
- **R6**：下载完成后通过现有 `ApkFileProvider` 和系统安装器安装，不改变安装权限模型。
- **R7**：旧版本仍无法自动更新时，必须提供可直接用浏览器打开的手动 APK 地址。

## 边界与非目标

- 不引入第三方下载 SDK；
- 不要求 HTTPS 证书或域名；
- 不改变 APK 签名、包名和 FileProvider；
- 不解决旧版二进制本身没有 WebView 下载代码的问题；旧版用户需要手动安装一次 1.0.85；
- 不覆盖真实 Android 设备上的系统安装器交互测试，本环境没有 adb 设备。

## 验收标准

- **AC1**：页面能用 fetch 从生产下载地址取得完整 APK，接收字节等于 Content-Length。
- **AC2**：完整 APK 被拆成至少 2 个不超过 64KB 的分片写入。
- **AC3**：传输完成后调用 `finishWebUpdate`，前端进度显示 100%。
- **AC4**：下载失败时进度文字为「失败」，按钮为「重试下载」，浏览器下载按钮可见。
- **AC5**：Android 工程编译通过，产出可签名 APK。
- **AC6**：生产 `/api/app/latest` 返回 1.0.85 / versionCode 86，APK 地址可访问。
- **AC7**：真实手机点击安装需人工验证（当前环境无真机，标记未验证）。

## 依赖与风险

- 依赖 WebView 允许混合内容（项目已设置 `MIXED_CONTENT_ALWAYS_ALLOW`）；
- 依赖下载接口允许 CORS（服务端已设置 `Access-Control-Allow-Origin: *`）；
- JS Bridge 单次字符串为 64KB 原始数据对应的 base64，约 87KB，避免大字符串风险；
- 如果用户当前版本过旧，必须先手动安装一次新版；
- 系统「安装未知应用」权限仍需用户确认。

## 待确认问题

- 无阻塞问题；真实设备安装器行为需上线后用户验证。
