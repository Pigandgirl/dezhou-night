# 系统响应与稳定性优化需求文档

## 背景

用户反馈希望整套系统运行更快、更流畅、响应更稳定。当前主要体感问题：

- `/play` 单文件 HTML 原始大小约 **3.2MB**；
- 服务器返回 HTML 时没有压缩；
- 每次打开游戏都要传输完整 HTML；
- 192 个语音 MP3 被 base64 内联进 HTML，导致首包和解析体积过大；
- 服务器部分热路径存在重复磁盘读取或重复序列化。

## 代码库扫描发现的高优先级点

1. **静态 HTML 未压缩**：3.2MB 直接发送，移动网络首屏慢。
2. **无 ETag/304**：回访仍然重新传输完整 HTML。
3. **语音 MP3 全部内联**：HTML 中的音频 base64 约 2.1MB，拖慢解析。
4. **`currentAppVersion()` 每次读盘解析 `latest.json`**：所有版本门禁请求都走同步 I/O。
5. **`dayKey()` 每次创建 Intl.DateTimeFormat**。
6. **`broadcastState()` 零散客户端时可能重复 stringify 同一状态帧**。
7. **构建/部署没有为外置语音资产做处理**。

## 优化目标

- 首屏 HTML 传输体积显著降低；
- 回访请求命中 304；
- 游戏逻辑不再等待不必要的同步磁盘读取；
- 语音资源按需加载，不参与首屏解析；
- APK 与网页都能正确访问外置语音文件；
- 不改变玩法、UI 和语音功能；
- 响应优化必须可测量，而不是只做代码审查。

## 需求点

- **R1** 对 HTML/JS/JSON 等文本静态资源启用 Brotli/Gzip 压缩。
- **R2** 静态资源增加 ETag 与条件请求 304，HTML 使用 no-cache 而非 no-store。
- **R3** 启动时预热主 HTML 压缩缓存，避免首个用户承担压缩成本。
- **R4** 版本清单 `latest.json` 增加 mtime 缓存，减少每次版本校验读盘。
- **R5** 缓存 `Intl.DateTimeFormat`，避免重复构造。
- **R6** SSE 状态广播复用正常/观战 JSON 帧，减少重复序列化。
- **R7** 语音 MP3 从 HTML 中移出，放到 `public/voice`，按当前音色懒加载。
- **R8** APK 使用扁平 `voice_*.mp3` 文件名，规避 Windows aapt2 反斜杠目录。
- **R9** 网页通过 `/voice/...` 提供语音文件，带 24 小时缓存。
- **R10** 构建和部署脚本同步上传语音资源，保证网页/APK 不缺失。

## 非目标

- 不改写 3D 渲染架构；
- 不替换 Three.js；
- 不改变游戏规则；
- 不引入 Redis/数据库；
- 不做 CDN（当前是单机 Node 服务）；
- 不做 Service Worker 强制缓存策略变更。

## 验收标准

- **AC1** 生产 `/play` 使用 Brotli 后 wire size 从约 3.2MB 降到 300KB 以下。
- **AC2** 生产 `/play` 支持 gzip/br，响应头含 `Vary: Accept-Encoding`。
- **AC3** ETag 条件请求返回 304，0 字节。
- **AC4** 优化后 HTML 原始大小从约 3.2MB 降到约 1MB。
- **AC5** 语音 MP3 外置，网页 `/voice/<profile>/<clip>.mp3` 200；浏览器首次加载当前音色 24 个文件并成功解码。
- **AC6** APK 内包含 192 个扁平 `assets/voice_*.mp3`，无嵌套反斜杠目录。
- **AC7** 页面无 JS 错误，启动正常。
- **AC8** 版本清单/日期格式化/SSE 帧优化通过语法与行为测试。
- **AC9** Android 1.0.92 构建通过。
- **AC10** 真机 APK 语音播放需人工验证（无设备）。

## 风险

- APK 体积从约 1.28MB 增至约 2.01MB，换取更小 HTML 解析和按需语音加载；
- Brotli 首次压缩需要 CPU，已通过启动预热规避；
- 新 `/voice` 路由依赖部署脚本上传静态文件；
- Windows aapt2 的路径分隔符问题已通过扁平文件规避；
- 真实网络和低端机仍需线上验证。
