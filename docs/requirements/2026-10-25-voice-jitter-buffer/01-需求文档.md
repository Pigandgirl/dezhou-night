# 语音卡顿优化需求文档

## 背景与问题

用户反馈：能听到其他玩家说话，但声音一卡一卡、断断续续，无法听清完整一句话，听感非常累。

现有链路：

```text
麦克风 -> ScriptProcessor 4096 -> 16k PCM
  -> 每块经一次 HTTP POST
  -> 服务器 SSE 广播 base64
  -> 每个包创建 AudioBufferSource
  -> 60ms 播放缓冲
```

## 当前市场常见方案调研

### 1. WebRTC + Opus

WebRTC 的 NetEQ 是行业标准：

- Opus 低码率语音编码；
- 自适应 jitter buffer（抖动缓冲）；
- 丢包隐藏 PLC / Opus FEC；
- NetEQ 时间伸缩，避免断音；
- 浏览器原生 WebRTC、回声消除、自动增益。

Discord、Zoom、Google Meet 等都是这个方向。

本项目之前测试过 WebRTC P2P：

- Android 运营商 NAT 下 STUN 不通；
- 公网 TURN 不可达；
- 服务端 TURN 端口未开放。

所以没有继续使用 WebRTC。

参考：

- https://crates.io/crates/neteq
- https://github.com/selkies-project/selkies/issues/153

### 2. WebSocket + Opus + 自建 jitter buffer

Mumble/Discord 一类语音常用：

- 持久 WebSocket；
- Opus 编码；
- 20ms 语音帧；
- 接收端抖动缓冲；
- 丢包隐藏。

优点：可控、无需浏览器 WebRTC/TURN。
缺点：需要自己实现 jitter buffer，Opus 集成成本更高。

### 3. Web Audio + AudioWorklet 环形缓冲

Web Audio 播放常见问题是逐包 `AudioBufferSourceNode` 调度，网络抖动会直接产生空隙。AudioWorklet 可以把 PCM 写入环形缓冲，在音频线程连续读取，听感更平滑。

参考：

- https://stackoverflow.com/revisions/24567ed8-f12c-40d3-960c-ab1ca7033703/view-source
- https://github.com/shootao/esp_elastic_pcm_buffer

### 4. 商用 RTC SDK

声网 Agora、即构 ZEGO、腾讯 TRTC 等直接提供：

- Opus 编解码；
- 自适应抖动缓冲；
- 丢包隐藏；
- 回声消除；
- 全球中继。

代价是接入成本、按分钟计费和账号依赖。本项目目前是自建轻量语音，不适合立即引入商用 SDK。

## 本项目选择

考虑现有架构、服务器和 Android WebView 兼容性，采用：

```text
WebSocket 二进制 PCM
+ 20ms 分帧
+ 320-550ms 自适应 jitter buffer
+ 完整 HTTP 队列兜底
+ 服务端 WS/SSE 互通
```

这不是替代 WebRTC 的完整方案，但针对“能听到但断断续续”能直接解决根因。

## 根因

1. **上传丢帧**：旧代码 `sendInFlight` 时只保留最后一个 `pendingPcm`，网络稍慢就丢中间语音。
2. **HTTP 每块一次请求**：每 85ms 一个 HTTP POST，移动网络下 RTT 抖动大。
3. **60ms 播放缓冲过小**：任何网络抖动都会 underrun。
4. **underrun 恢复太激进**：重置为 60ms 立刻播放，马上又断。

## 功能需求

- **R1**：语音上行改为持久 WebSocket，不再每帧一个 HTTP 请求。
- **R2**：音频按 20ms 分帧发送，二进制传输，不使用 base64。
- **R3**：服务端给每个 WS 帧加 `pid + seq` 头，支持接收端识别说话人和顺序。
- **R4**：播放端预缓冲 320ms 起步，自适应增长到 550ms。
- **R5**：WS 不可用时保留 HTTP+SSE 兜底；HTTP 上传改为完整队列，不再覆盖丢帧。
- **R6**：WS 与 SSE 双向互通，新老发送端都能被接收。
- **R7**：接收端在 WS 可用时忽略重复 SSE，避免双声。
- **R8**：保留逐人禁音、只听、全部静音和电平显示。
- **R9**：语音面板继续显示上传/接收包数。
- **R10**：允许 300-500ms 延迟，优先连贯清晰。

## 非目标

- 不实现 Opus 编解码；
- 不实现 WebRTC；
- 不实现 AudioWorklet 环形缓冲（作为下一步可选优化）；
- 不做丢包 FEC；
- 不改变 16k 单声道语音规格。

## 验收标准

- **AC1**：发送端 WebSocket 连接成功，`wsActive=true`。
- **AC2**：发送端 20ms 分帧，接收端接收包数与发送包数一致，无丢帧。
- **AC3**：接收端 AudioContext 始终 running，jitterTarget ≥0.32。
- **AC4**：禁用 WebSocket 时 HTTP 兜底仍能完整接收，队列清空。
- **AC5**：同一句话连续播放，不再因 60ms underrun 反复断音。
- **AC6**：逐人禁音/只听/全部静音不回归。
- **AC7**：Android 构建 1.0.87 成功。
- **AC8**：真机听感需上线后人工验收（当前环境无真机）。

## 依赖与风险

- Android WebView 对 `ws://` 混合内容可能有限制；已实现 HTTP 队列兜底；
- WS 版本门禁要求客户端为最新版本；
- 320ms 缓冲会增加延迟，符合“可以有延迟但不要断”的要求；
- 后续可升级 Opus + AudioWorklet。

## 待确认问题

- 真实手机听感是否达到“连贯听清一句话”；需要用户实测反馈。
